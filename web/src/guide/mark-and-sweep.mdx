We have blocks full of cells, and nothing that frees them. Let's look again at what the compiler emits for a function that makes a few strings.

<Pair>

```js
function greet() {
    let a = "hello";
    let b = " world";
    let c = a + b;
    return c;
}
```

```c
JSValue greet(void) {
    JSValue a = js_new_string("hello", 5);
    JSValue b = js_new_string(" world", 6);
    JSValue c = js_add(a, b);
    return c;
}
```

</Pair>

Say memory runs low inside `js_add`, while it allocates the joined string. That's when we'd like to free the strings nobody uses anymore. `a` and `b` are clearly still in use: `js_add` is reading them. But to the runtime, `a`, `b` and `c` are just C locals of `greet`. Nothing in this function tells it they exist. So how can it know what's still in use?

## What is garbage?

A cell is alive if the program can still reach it. The program starts from a few places, the *roots*: its global variables, and the local variables of every function that hasn't returned yet. From a root, it can follow a pointer to a cell, and from that cell to the next. Anything it can't reach this way, it can never use again. That's garbage.

```js
function greet() {
    let a = "hello";
    let b = " world";
    let c = a + b;   // a, b and c are all reachable
    return c;        // the caller gets c: a and b are garbage
}
```

Most garbage collectors are some form of *mark and sweep*, and so is ours.

- **Mark.** Start from the roots, and mark every cell the program can reach.
- **Sweep.** Free every cell that isn't marked.

While the collector runs, the program waits, so nothing changes under it. This is called *stopping the world*. It's the simplest way to collect, and we'll make it smarter in later chapters.

## The heap

Everything the collector knows lives in one struct, the heap. The allocators and blocks are from [Custom Allocation](/guide/custom-allocation). The rest is new.

```c
typedef struct {
    JSAllocator  alloc[32];          /* one per size class */
    JSBlock     *blocks[32];         /* every block of each class */
    size_t       allocated;          /* bytes allocated since the last collection */
    size_t       next_gc;            /* collect when `allocated` reaches this */

    JSValue     *globals;            /* the global variables */
    size_t       global_count;
    void        *stack_base;         /* the top of the C stack */

    JSCell     **mark_stack;         /* cells marked, not visited yet */
    size_t       mark_count;
} JSHeap;

static JSHeap heap;
```

## Marking

Where do we keep a cell's mark? A bit in the cell's header would work, but then forgetting the last collection's marks means writing to every cell, and the sweep would have to read every cell, dead or alive, to see its mark. So the marks sit next to the allocation bits, in a second bitmap per block.

```c
typedef struct JSBlock {
    struct JSBlock *next;
    uint32_t cell_size;
    uint32_t cell_count;
    uint8_t  size_class;
    uint64_t alloc_bits[64];   /* a bit per cell: in use */
+     uint64_t mark_bits[64];    /* a bit per cell: reachable */
} JSBlock;
```

Clearing every mark of a block is one `memset`, and the cell header stays as small as it was in Strings. Nothing in it is for the collector.

Marking a cell sets its bit in its block's mark bitmap. The block and the index both come from the cell's address.

```c
static bool set_mark(JSCell *c) {
    JSBlock *b = js_block_of(c);
    uint32_t i = cell_index(b, c);
    uint64_t bit = UINT64_C(1) << (i % 64);
    if (b->mark_bits[i / 64] & bit) return false;   /* already marked */
    b->mark_bits[i / 64] |= bit;
    return true;
}
```

Then we need to mark everything the cell points to, and what that points to, and so on. Each kind of cell knows what it points to: a rope points to its two halves, a slice to its parent, and a flat string to nothing. So each kind gets a `visit` function.

```c
static void visit(JSCell *c) {
    switch (c->kind) {
    case JS_CELL_STRING:
        break;                                    /* holds no pointers */
    case JS_CELL_ROPE:
        mark_value(((JSRope *)c)->left);
        mark_value(((JSRope *)c)->right);
        break;
    case JS_CELL_SLICE:
        mark_value(((JSSlice *)c)->parent);
        break;
    }
}
```

The obvious way to write `mark` is recursion: mark a cell, then call `mark` on its children. But a rope built by a loop of `+=` can be a million levels deep, and so can a linked list. Recursion that deep overflows the C stack. So `mark` pushes the cell on the heap's mark stack instead, and `drain` visits them one by one.

```c
static void mark(JSCell *c) {
    if (set_mark(c)) push(c);   /* newly marked: visit it later */
}

static void mark_value(JSValue v) {
    if (js_is_pointer(v)) mark(js_as_cell(v));
}

static void drain(void) {
    while (heap.mark_count) visit(heap.mark_stack[--heap.mark_count]);
}
```

A cell that's already marked isn't pushed again, so cycles end too.

<Note>

In [String Optimizations](/guide/string-optimizations), the compiler writes string literals into the binary instead of allocating them. They're in no block and have nothing to free. They carry a *static* flag in their header, and `mark` skips them.

</Note>

## Marking the roots

Marking starts from the roots. Global variables are easy. The compiler puts them in one array, and `main` tells the heap where it is, once.

<Pair>

```js
let total = 0;
```

```c
static JSValue mod_globals[1];

int main(int argc, char **argv) {
    js_register_roots(mod_globals, 1);
    ...
}
```

</Pair>

Marking them is a loop.

```c
static void mark_roots(void) {
    for (size_t i = 0; i < heap.global_count; i++)
        mark_value(heap.globals[i]);
}
```

Local variables are the hard part. A JavaScript local is a C local, like `a`, `b` and `c` in `greet`. The C compiler decides where each one lives: in a register, in the stack frame, or nowhere at all if it optimized it away.

We could have every function register its locals when it starts, and unregister them when it returns. That's called a *shadow stack*, and every call would pay for it. Instead, `greet` stays exactly as it is, and we look at the C stack itself. Every local that's not in a register is in its function's stack frame. So we scan it: every word from the collector's own frame up to `stack_base`, the top of the stack that `main` records when the program starts, might be a pointer.

```c
static void mark_stack(const void *low) {
    for (const uintptr_t *p = low; p < (uintptr_t *)heap.stack_base; p++) {
        JSCell *c = find_cell(*p);   /* the cell at this address, or NULL */
        if (c) mark(c);
    }
}
```

This is called *conservative* scanning. We can't tell a real pointer from an integer that happens to look like one, so we treat both as pointers. At worst, a dead cell lives a little longer.

### Finding a cell

The scan asks, for every word on the stack, "is this the address of a cell?" Thanks to blocks, that's a few steps, and almost every word fails at the first one.

```c
static JSCell *find_cell(uintptr_t w) {
    if (w < heap.min_addr || w >= heap.max_addr) return NULL;   /* outside the heap */
    uintptr_t base = w & ~(uintptr_t)(JS_BLOCK_SIZE - 1);
    if (!block_set_contains(base)) return NULL;
    JSBlock *b = (JSBlock *)base;
    uint32_t i = (w - base - JS_BLOCK_FIRST_CELL) / b->cell_size;
    return bit_get(b->alloc_bits, i) ? block_cell(b, i) : NULL;
}
```

- **The range check.** The heap knows the lowest and highest addresses it has mapped. NaN-boxing helps here: every double and every integer `JSValue` has a tag in its top 16 bits, so it's far outside the range. A pointer `JSValue` is the address itself.
- **The block set.** Masking gives a 64 KiB-aligned address, but is it one of our blocks? The heap keeps a hash set of its blocks.
- **The index.** Dividing gives the cell the word points into. It doesn't have to point at the start: the C compiler may keep a pointer into the middle of a cell, like into a string's characters, and that still keeps the cell alive.
- **The allocation bit.** The word may point at a free cell. Only a cell in use counts.

### Registers

There's one catch. When `js_add` runs out of memory, `a` and `b` may be in registers, not on the stack. So before scanning, we save the registers to the stack. `setjmp` does exactly that: it saves them into a `jmp_buf`, and that `jmp_buf` is a local, on the stack.

```c
JS_NOINLINE void js_gc(void) {
    jmp_buf regs;
    setjmp(regs);        /* the registers, now on the stack */
    collect(&regs);      /* scans from here up */
}
```

## Sweeping

In [Custom Allocation](/guide/custom-allocation), freeing a cell was clearing its allocation bit. We could call `free_cell` on every unmarked cell, but there's a shortcut. After marking, a cell is in use if and only if it's marked. So sweeping a block is copying its mark bits to its allocation bits, and one write frees 64 cells.

```c
static uint32_t sweep_block(JSBlock *b) {
    uint32_t live = 0;
    for (uint32_t w = 0; w < (b->cell_count + 63) / 64; w++) {
        b->alloc_bits[w] = b->mark_bits[w];
        live += popcount64(b->mark_bits[w]);
    }
    return live;
}
```

That's at most 64 words per block, and no dead cell is touched. A dead cell isn't freed or cleared. Its allocation bit is clear now, so the allocator will hand it out again.

### Lazy sweeping

We don't even sweep right away. The collection only puts every block in a queue. When the allocator of a class runs out of cells, it sweeps the next block of its class in the queue, and allocates from that. So the sweep is spread over the program's own allocations, and the collection's pause is just the marking.

A block that turns out to have no live cells at all goes to a pool of empty blocks, and any class can take it.

There's one trap. A block still waiting in the queue has stale allocation bits: they still count the cells that died. If a stale word on the stack points to one of those, the scan would mark a dead cell and bring it back, after its children may already have been reused. So a collection first sweeps whatever is left in the queue. Then the allocation bits are exact.

## Collecting

And here is the whole collection.

```c
static void collect(const void *stack_low) {
    finish_sweeping();         /* exact allocation bits for the scan */
    clear_marks();             /* memset every block's mark bits */
    mark_roots();              /* the globals */
    mark_stack(stack_low);     /* the locals */
    drain();
    queue_sweep();             /* every block: swept when the allocator needs it */
    heap.allocated = 0;
}
```

The allocator's slow path calls `js_gc`, once the program has allocated enough since the last collection.

```c
void *js_alloc_slow(unsigned size_class) {
+     if (heap.allocated >= heap.next_gc) js_gc();
    ...
}
```

Let's go back to `greet` and follow it through. Memory runs low inside `js_add`.

1. `js_add` allocates the joined string, and the allocator's slow path calls `js_gc`.
2. `js_gc` saves the registers on the stack, and `mark_stack` scans from there up. Somewhere on it, in `greet`'s frame or a saved register, are `a` and `b`. Both are marked.
3. `drain` visits them. They're flat strings, which point to nothing, so marking is done.
4. Every block goes in the sweep queue. The strings the program made earlier and no longer reaches will be reused.
5. `js_gc` returns, the allocator sweeps a block, finds a free cell, and `js_add` carries on with `a` and `b`.

`greet` never knew a collection happened. Once it returns, its frame is gone. Nothing reaches `a` and `b` anymore, so the next collection frees them, while `c` lives on in whoever called `greet`.

## When to collect

We collect once the program has allocated 4 MB since the last collection. That's not quite right for a big program: if 100 MB are alive, collecting every 4 MB means marking 100 MB for every 4 MB allocated. So after each collection, we let the heap grow in proportion to what survived. Then the time spent collecting stays a fixed share of the program's time. We'll come back to this in [Young and Old Generations](/guide/generations).

## Cells never move

Many collectors *move* the cells that survive, packing them together so that memory isn't fragmented. Moving a cell means updating every pointer to it.

We can't do that, because we scan the stack conservatively. A word on the stack might be a pointer, or it might be an integer that happens to look like one. We can't rewrite it, because if it's an integer, we've just changed the program's data. So in visaljs, a cell stays where it was allocated for its whole life. Size classes keep the holes it leaves useful.

## What's next?

Allocation is fast, sweeping costs almost nothing, and the generated code doesn't know the collector exists. But the marking still stops the program, for as long as it takes to visit every live cell. With hundreds of megabytes alive, that's hundreds of milliseconds without running the program.
