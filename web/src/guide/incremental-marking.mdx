Our collector stops the program until it has marked every live cell. With a few megabytes alive, that's a millisecond, and nobody notices. With 500 MB alive, the program freezes for half a second. A server stops answering requests, and an animation skips frames.

The sweep is already spread out, a block at a time. Let's do the same with the marking: mark a little, let the program run, mark a little more. Each piece is a *slice*.

## Three colors

It helps to think of each cell as having one of three colors during a marking.

- **White.** Not marked. If it's still white at the end, it's garbage.
- **Grey.** Marked, but not visited yet: it's on the mark stack, and its children may still be white.
- **Black.** Marked and visited: all its children are marked.

Our mark bit and mark stack already work this way. Marking turns a cell grey, and visiting it turns it black. The marking is done when nothing is grey.

## The lost cell

Between two slices, the program runs and changes pointers. That can break the marking.

```js
// marked so far: a is black, b is grey, the {} is white
a.x = b.y;     // the {} is stored into a black cell
b.y = null;    // and removed from the grey one
```

The marker already visited `a`, and it never will again. When it visits `b`, the `{}` isn't there anymore. So the `{}` stays white, the sweep frees it, and `a.x` points to freed memory.

This happens only when the program does both: it stores a white cell into a black one, and removes every other path to it from a grey one. If we stop either of them, nothing is lost.

## The write barrier

We stop the first. Whenever the program stores a pointer into a cell during a marking, we mark what it stored. A black cell can then never point to a white one. This is Dijkstra's *write barrier*: a bit of code that runs on every store.

Every store of a `JSValue` into a cell goes through one function, `js_store`. Setting a property, writing an array element, assigning a captured variable: the runtime does them all with `js_store`, never with a plain `=`.

```c
static inline void js_store(JSContext *ctx, JSCell *owner, JSValue *slot, JSValue v) {
    *slot = v;
    if (JS_UNLIKELY(ctx->rt->marking) && js_is_cell(v))
        mark(ctx->rt->marker, js_as_cell(v));   /* white turns grey */
}
```

Outside a marking, the barrier is one compare that's never taken. That's cheap, but it runs on every store, which is why it's inlined.

<Note>

Only stores into cells need the barrier, not stores into C locals. That's what keeps it affordable, but it means the stack isn't watched. We come back to this in the final pause.

</Note>

## Marking in slices

A marking now has three parts.

1. **Start**, in a short pause. Finish the sweep from the last collection, clear every mark bit, and mark the roots and the stack.
2. **Slices**, while the program runs. Each slice visits grey cells for a while, then lets the program go on.
3. **The final pause.** Mark the roots and the stack again, and visit what's left.

### Who pays for a slice?

The program runs slices as it allocates. Every 256 KB allocated, the allocator's slow path runs a slice. The more the program allocates, the more the marker has to keep up with, so the slice's size grows with the allocation: it marks a fixed number of bytes for every byte allocated since the last slice.

We pick that ratio so the marking finishes by the time the program has allocated about an eighth of the live heap. That's how much the heap grows during the marking. A slice marks at most 4 MB, about a millisecond. If one big allocation, like a large array, asks for more, the rest is owed and paid by the next slices.

### New cells

A cell allocated during the marking is white. It's still safe.

- If the program stores it into a black cell, the barrier marks it.
- If it's only in a local, the final pause finds it on the stack.

### The final pause

The stack has no barrier, so the stack the marker saw at the start says little about the stack now. And the roots, like global variables, are written without `js_store` too. So the final pause marks the roots and scans the stack again, then drains what that found. Usually that's little, since most of the heap was marked already. The pause is about the size of the stack, not the size of the heap.

A cell that died after the marker reached it is still marked, so it survives until the next collection. This is *floating garbage*, and it's the price of not stopping the world.

<Note>

Checking builds verify the barrier. In the final pause, before scanning the stack again, every black cell must point only to marked cells. A store that skipped `js_store` stops the program right there, naming the cell.

</Note>

## When it's worth it

A marking in slices costs more in total than one pause: the barrier's slow path, and the floating garbage. With a small heap, a full pause takes a millisecond or so anyway. So we mark incrementally only when 8 MB or more survived the last collection. Below that, we just stop the world.

## What's next?

The marking no longer stops the program for long, but it still visits every live cell, every time. Most cells in a program die young, and the ones that survive tend to live for a long time. Marking those again and again is wasted work. Next, we split the heap in two, in [Young and Old Generations](/guide/generations), and the barrier we just built does the work there too.
